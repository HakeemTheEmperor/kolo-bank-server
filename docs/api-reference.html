Kolo API
Kolo API Reference

Build on Kolo

Kolo is a mock banking core: ledger accounts, cards, internal and external transfers, and merchant collections — all reachable over a single JSON API. This reference documents every endpoint exactly as implemented, including every error you can actually hit.

Authenticate a request → Create your first charge → Listen for events → Handle errors →

Base URL

Kolo runs as a self-hosted Docker stack rather than a shared public API — point requests at wherever your instance is deployed. Locally, that's http://localhost:8080 after make up. This page itself is served at /docs on that same host.

Format

Every request and response body is JSON. Amounts are always integers in the currency's minor unit — amount_minor: 250000 on currency NGN is ₦2,500.00, never a float.

Two ways in

An API key authenticates a merchant's server-to-server integration (charges, payouts, checkout). A session token authenticates a logged-in person — a merchant's dashboard, or a customer's own account.

Idempotent by default

Every endpoint that moves money or creates a resource accepts (and most require) an Idempotency-Key header. Retry safely — you'll never double-charge or double-send.

Authentication

Every request carries its credential the same way: an Authorization: Bearer <token> header. Which kind of token you send determines which routes you can call.

API keys — merchant integrations

Used on /v1/tokens, /v1/charges, /v1/payouts, and /v1/checkout-sessions. Created from the merchant dashboard (see Create a key). Each key carries a mode (sandbox or live) and a list of scopes that gate individual routes.

Session tokens — logged-in people

Used on /v1/dashboard/* (merchant dashboard actions) and /v1/me/* (a customer's own transfers, cards, disputes, connected apps). Issued at login; must have completed MFA, or every route rejects with 401.

curl
# Any authenticated route looks like this
curl https://your-kolo-host/v1/charges \
  -H "Authorization: Bearer kolo_test_51a9c...e2f0"
Scopes

An API key's scopes are assigned when it's created (Create a key) and are free-form strings — only the five below are ever checked by a route. A key without the required scope for a route gets 403 forbidden.

ScopeGrants
charges:writeCreate tokens and charges
charges:readList and retrieve charges
payouts:writeCreate payouts
payouts:readList and retrieve payouts
checkout:writeCreate and retrieve checkout sessions — there's no separate read scope
Ownership, not permission, guards everything else Getting someone else's charge, payout, checkout session, API key, card, or dispute by ID doesn't return 403 — it returns 404, identical to the ID not existing at all. This is deliberate: it means an attacker probing IDs can't even confirm a resource exists.

Test and live modes

Every API key is minted into exactly one mode, permanently — there's no per-request switch. Everything the key touches (tokens, charges, payouts, checkout sessions, webhook deliveries) inherits that mode and stays fully isolated from the other.

ModeKey prefixBehavior
sandboxkolo_test_…Simulated money movement — safe for integration testing, including deliberately failing test cases via marker strings (see individual endpoints).
livekolo_live_…Same simulated rails under the hood (this is a mock banking core end to end), kept in a separate data partition from sandbox so dashboards and reporting never mix the two.

List endpoints (charges, payouts, API keys, webhook endpoints) only ever return rows in the calling key's own mode. A sandbox key cannot see, charge against, or receive webhooks for anything created in live mode.

Idempotency

Any endpoint that creates a resource or moves money requires an Idempotency-Key header — a string you generate (a UUID is a good default). Send the same key twice with the same intent and you get back the original result, not a duplicate.

curl
curl https://your-kolo-host/v1/charges \
  -X POST \
  -H "Authorization: Bearer kolo_test_51a9c...e2f0" \
  -H "Idempotency-Key: 7c3aa6c2-df1b-4a9e-9c9a-1d9e9d6b2f10" \
  -H "Content-Type: application/json" \
  -d '{"token_id":"tok_9f1c...","amount_minor":250000,"currency":"NGN"}'
Omitting it fails closed, not open A missing or blank Idempotency-Key on a route that requires one returns 400 missing_idempotency_key before your request body is even read — it never silently processes without one.

Card freeze/unfreeze/limits, dispute creation, connected-app revocation, and account recovery don't require the header — each endpoint's Headers panel below states explicitly whether it's required.

Errors

Every error — auth, validation, or server-side — comes back as the same shape, at the matching HTTP status code.

Error response
{
  "error": {
    "code": "insufficient_balance",
    "message": "insufficient available balance"
  }
}

There is no numeric or nested error hierarchy — code is a stable, greppable string you can switch on, and message is human-readable and may change wording over time. Successful responses are never wrapped — a charge object is returned exactly as shown in its endpoint's example, with no enclosing data key; list endpoints return a bare JSON array.

StatusMeaning
400The request itself is malformed — bad JSON, an invalid amount/currency, a missing idempotency key, an out-of-range field.
401Missing, invalid, expired, or not-yet-MFA'd credential.
403Valid credential, wrong scope or wrong identity kind (e.g. an individual calling a business-only dashboard route).
404Resource doesn't exist — or exists but isn't yours. Both look identical, by design.
409The resource exists but is in a state that can't accept this action — a matched-but-blocked transfer awaiting confirmation, an authorization not currently awaiting 3-D Secure, a recovery request not yet past its cooling-off window.
422Semantically valid request that the system understood but won't execute — insufficient balance, a tier limit exceeded, no settlement account in that currency.
429Rate limited — back off and retry.
500Something broke on Kolo's side. Safe to retry with the same idempotency key.

Pagination & rate limits

Pagination

List endpoints (charges, payouts) accept ?limit=, default 25, maximum 100. An invalid or non-positive value is silently treated as the default rather than erroring. There's no cursor — lists return the most recent N by creation time.

Rate limits

API-key routes: 10 requests/second per key, burst 20. The public, unauthenticated recovery endpoints are limited by caller IP instead: 0.5 requests/second, burst 5. Both return 429 rate_limited when exceeded. Session-authenticated dashboard and customer routes aren't rate limited at this layer.

Webhooks

Register an endpoint (Add an endpoint) and Kolo will POST a JSON payload to it every time a charge or payout you own reaches a terminal state. Full event and signature reference: Event types & signing.

Customer · Transfers

A customer sending money to another Kolo customer by email — session-authenticated, from the customer's own account. Kolo checks the recipient's name against the account on record and, for large or first-time transfers, holds the funds in a cancellable cooling-off window rather than sending immediately.

POST/v1/me/transfers

Send a transfer

SessionIdempotency-Key required
Body
FieldTypeRequired
recipient_emailstringrequiredMust belong to an existing Kolo identity with an open account.
recipient_namestringrequiredWhat the sender typed as the recipient's name — checked against the account on record.
amount_minorintegerrequiredMinor units.
currencystring(3)required3-character currency code.
confirm_mismatchbooleanoptionalSet true to proceed anyway after a 409 name-mismatch response.
Response shape varies by outcome

A low-risk transfer settles immediately (outcome: "completed", transaction_id set). A high-risk one — first-time payee, an unusually large amount, or a name mismatch you've confirmed — is held instead (outcome: "held", pending_id and release_at set, no transaction_id). reasons lists why, when present.

Errors
  • 400invalid_requestMalformed JSON body.
  • 400invalid_amountCurrency must be exactly 3 characters.
  • 422no_accountYou have no open account.
  • 404not_foundRecipient email doesn't match an existing identity.
  • 409Name mismatch, not yet confirmed — body is {"outcome":"blocked","payee_result":"…"}, not the standard error envelope. Retry with confirm_mismatch: true to proceed.
  • 422limit_exceededExceeds your KYC-tier transfer limit.
  • 422insufficient_balanceNot enough available balance.

Webhook event types & signing

A charge or payout starts pending and settles asynchronously against a simulated rail. Rather than polling, register an endpoint and Kolo notifies you the moment it reaches a terminal state.

Event types
EventFires when
charge.succeededA charge's linked transfer completes.
charge.failedA charge's linked transfer fails.
payout.succeededA payout's linked transfer completes.
payout.failedA payout's linked transfer fails.

Delivery only ever goes to active endpoints registered in the matching mode — a sandbox charge never fires a live endpoint, and vice versa.

Request

A POST to your url, 5-second timeout, with these headers:

Header
Content-Typeapplication/json
X-Kolo-EventOne of the four event types above.
X-Kolo-Signaturesha256=<hex hmac> — see verification below.
Retry schedule

Anything other than a 2xx response (including a timeout) counts as a failure. Up to 5 attempts total, backing off 1 min → 5 min → 30 min → 2 hr. After the 5th failed attempt, the delivery is marked permanently failed — no further retries.

Payload

No enclosing envelope — the event type lives only in the X-Kolo-Event header, and the body is exactly the object below:

POST https://shop.example/webhooks/kolo
X-Kolo-Event: charge.succeeded
X-Kolo-Signature: sha256=1f0ab6...9c7e
Content-Type: application/json

{
  "id": "ch_4b1f7c90",
  "amount_minor": 250000,
  "currency": "NGN",
  "status": "succeeded"
}
Verifying a delivery

Recompute the HMAC-SHA256 of the raw request body using your endpoint's secret (from Add an endpoint), hex-encode it, and compare against the value after sha256= — reject the delivery if they don't match.

Go
// secret is the whsec_… value shown once when the endpoint was created
mac := hmac.New(sha256.New, []byte(secret))
mac.Write(rawRequestBody)
expected := "sha256=" + hex.EncodeToString(mac.Sum(nil))

if !hmac.Equal([]byte(expected), []byte(r.Header.Get("X-Kolo-Signature"))) {
    // reject — signature mismatch
}
